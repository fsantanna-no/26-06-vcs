# Lemmy: comparison target and possible corpus

# 1. Relevance

- Lemmy = federated Reddit: communities, posts, comments, up/down
  votes, per-community moderators, per-instance admins, public
  modlog, instance-level blocking (defederation); ActivityPub
- the closest DEPLOYED decentralized forum to our target: same
  objects as our corpora (posts, votes, removals) plus something
  none of them has: MANY INSTANCES holding the same community
  with different moderation and different visibility
- more relevant than Mastodon (microblog) or Aether (dead-ish);
  Kbin/Mbin and PieFed are the same family
- verdict: yes, the reference application for 5.3 and the one
  corpus that maps onto the P2P plan (instances = peers)

# 2. Consensus

- none: each instance stores its own copy of federated objects;
  ordering by local timestamps; delivery best effort
- moderation actions federate as activities (Remove, Delete,
  Block) but each instance decides whether to apply them
- defederation splits the view: the same community differs by
  instance, permanently -- a de-facto hard fork with no rule
- confirm from docs: how conflicting removals are resolved (they
  are not; last writer per instance)

# 3. Moderation

- three levels: community mods (remove, lock, ban from
  community), instance admins (site ban, purge, remove
  community), instance blocklists (defederation)
- public modlog per instance: action, target, reason, moderator
  (names hideable since 0.19); `/api/v3/modlog`
- removed posts stay in the database (`removed=true`); content
  hidden publicly but kept for mods and often retained by remote
  instances -> revoke WITH payload, as GitHub minimized
- blocklists: curated shared lists imported by many instances
  ("A Blocklist is a Boundary", below)

# 4. Votes

- up/down on posts and comments (downvotes can be disabled per
  instance); scores drive ranking
- federated as ActivityPub Like/Dislike carrying the voter's
  actor id -> per-vote, per-user, timestamped, visible to any
  federated instance (a known privacy debate; Kbin showed voters
  publicly)
- so votes are NOT anonymous at the protocol level, unlike SE
  dumps and Reddit: the first corpus with real per-user votes
  AND moderation reasons AND partitions

# 6. Simulation

- data access
    - posts, comments, communities, modlog: public REST API per
      instance, historical
    - per-user votes: NOT in the public API; obtainable by running
      a federated instance subscribed to target communities
      (prospective only), or from instance operators, or from
      Kbin/Mbin public voter lists (historical, partial)
    - defederation timeline: public blocklists + fediseer history
- mapping (lemmy-simple.lua, same lineage as gh-simple)
    - post/comment -> signed post by actor id
    - Like/Dislike -> like/dislike 1000 by the voter
    - modlog removal -> revoke by the moderator key WITH reason
      (spam, rule, off-topic), ban -> the member stops posting
    - one chain per community
- what it adds over the current corpora
    - per-user votes with named voters (GitHub had them, SE not)
    - removals with reason AND the moderator identity
    - INSTANCES: replay the same community as seen by N instances
      -> the P2P plan (260924-topology) gets real peers, real
      sync cadence (federation delays) and REAL PARTITIONS
      (defederation dates) instead of synthetic ones
- how it compares to the plans in ../2606-sims
    - single-peer replay: a GitHub-like run (~50k events), same
      driver shape, same metrics; expect dislike share and revoke
      rate between GitHub (9%, 5%) and wiki
    - P2P: the missing corpus for 260924-topology; instances =
      peers, defederation = partition schedule, blocklist import
      = a peer refusing a whole set of members
- pilot: one mid-size community on two instances that later
  defederated; posts + modlog historical, votes prospective if
  needed
- cost: a research instance federating with 1-2 big communities
  for a month collects votes; posts/modlog fetchable in a day
