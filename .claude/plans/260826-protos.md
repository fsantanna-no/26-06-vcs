# Real Protocols by Delivery and Consensus

## Context

- Intro paragraph (main.tex ~L82-88) claims gossiping reaches all
  users but lacks consensus
- Reality is a 3-level ladder; some systems do not even guarantee
  delivery
- Goal: classify real systems active in 2020+ (not necessarily
  academic) and rewrite the paragraph accordingly
- Definitions used here
    - deliver: every post eventually reaches every interested
      replica (all subscribers of a topic/room/feed)
    - consensus: all replicas agree on the same order and validity
      of posts (total order, conflict verdict)

## Merkle model vs delivery

- What buys delivery is HASH-LINKING (Merkle chain/DAG) or a
  Merkle-indexed set: missing data becomes detectable, and peers
  reconcile by pull (anti-entropy) instead of relying on push
- Every Level-0 system lacks it; every Level-1/2 system has it
- Farcaster is the instructive case: posts are hashed but NOT
  linked; hubs reconcile via a Merkle trie -> the property is
  "Merkle-based reconciliation", not "posts link to posts"
- Matches main.tex ~L1815: "Merkle DAGs simplify synchronization,
  provide persistence, and prevent duplication"

## Verbatim evidence (2026-08-26)

- Nostr (README): "Each person can publish their notes to
  multiple relays (which are just simple servers)"; "The hardest
  part is how to find in which relay you will find notes of each
  person you follow, since they can be anywhere". NIP-01: event
  id = "sha256 the serialized event"; references only via `e`
  tags (no chain). Relays "have any rule or internal policy they
  want" -> no delivery guarantee
- ActivityPub (W3C 7.1): delivery "SHOULD be performed
  asynchronously, and SHOULD additionally retry delivery to
  recipients if it fails due to network error"; objects are
  URIs, no hash chain. Mastodon code: `retry: 16, dead: false`;
  `FAILURE_THRESHOLDS = { days: 7 ...}` -> domain marked
  unavailable and deliveries skipped: `return unless ...
  DeliveryFailureTracker.available?(inbox_url)` -> posts to a
  7-day-down server are dropped
- gossipsub v1.0: mcache "segmented into 'history windows'";
  `mcache.shift()` "discarding messages older than the history
  length" (default 5 heartbeats) -> no persistence, late joiners
  miss posts; spec makes no delivery statement
- Scuttlebutt (protocol guide): "Each message (except the first
  one) references the ID of the previous message";
  createHistoryStream "is how peers ask each other for a list of
  messages in a particular feed"; feeds 3 hops out "replicated
  to help keep them available for others" -> hash chain + pull
- Bluesky/AT: "laid out in a Merkle Search Tree (MST) which
  reduces the state to a single root hash"; "Full repository
  exports can be fetched ... getRepo"; commit "contains both a
  reference to the previous repo revision ... and a copy of the
  previous root tree hash"; consumers "persist the sequence
  number ... as a cursor value when reconnecting" -> pull sync
- Farcaster (SPECIFICATION.md): gossipsub is "the primary
  delivery mechanism" but "Gossip alone cannot guarantee" it
  since "messages can be dropped or arrive out of order"; "Hubs
  must periodically select a random peer and perform diff sync
  to ensure strong eventual consistency" via a Merkle Patricia
  Trie; messages "uniquely identified by the hash of their
  contents"; CRDTs "achieve consensus without coordination"
  (i.e. convergence, not order)
- Matrix (S2S spec): "`prev_events` ... establishes a partial
  ordering on events within the room by linking them into a
  Directed Acyclic Graph (DAG)"; `/backfill`,
  `/get_missing_events` to "acquire the events it is missing";
  "a state resolution algorithm must be used to determine the
  resultant state" -> DAG + pull; consensus on state only
- Hypercore/Autobase (docs.pears.com): "secure, distributed
  append-only log"; Merkle proofs (`core.proof()`); single
  writer keypair; Autobase "linearizes that graph into an
  eventually consistent order" among added writers
  (`host.addWriter`) -> permissioned linearization
- Briar: "messages are synchronized directly between the users'
  devices"; "Every user who subscribes to a forum keeps a copy of
  its content" -> delivery only among contacts (Level 1, scoped)
- Aether/Mim: see entry below (pull sync, 6-month retention)

## Level 0: no delivery guarantee

- Nostr (2020, boom 2022+)
    - clients push events to chosen relays; relays "have any rule
      or internal policy they want" (README); the popular quotes
      "may (or may not) store" / "no guarantees of anything" could
      NOT be sourced to a primary document -> do not cite them
    - mitigation is social: publish to several relays
- ActivityPub / Mastodon (active)
    - server-to-server push with retries and backoff, then drop
    - only followers' servers are targeted; a server that was
      down long enough never gets the post
    - Raman IMC'19: outages and instance shutdowns cause data loss
- libp2p gossipsub / IPFS pubsub (active)
    - best-effort mesh; no persistence, late joiners miss posts
- Aether / Mim protocol (P2P forums; last commit 2021-07-20)
    - RECLASSIFY: delivery IS pull-based anti-entropy (Mim flows):
      "L does a POST request on R's index endpoint with a
      timestamp filter"; "R returns all new and updated entities
      since the timestamp"; "L determines which fingerprints it
      wants to request from R"
    - ephemeral, not lossy: "it's ephemeral. The content
      disappears after a while" (docs); FAQ: "Since there is no
      such thing as delete, it is up to each client to decide how
      long they want to serve a post"; reference client keeps
      posts 6 months, then stops distributing
    - entities have fingerprints (hashes) but no hash-linking
      -> Level 1 by delivery (within the 6-month window), no
      consensus; move out of Level 0
    - inactive since 2021 -> fails the "active 2020+" bar; keep
      only as a footnote or drop
- Briar: VERIFIED, belongs to Level 1 (scoped to contacts)

## Level 1: delivery, no consensus

- Scuttlebutt / Manyverse (active)
    - per-author append-only logs replicated along the follow
      graph; eventual delivery within hops
    - single-user consensus only (own feed); no multi-user order
- Bluesky / AT Protocol (2023+)
    - per-user Merkle repos on PDSs; relays crawl; anyone can
      sync a repo -> delivery is pull-able
    - no cross-user order; moderation via labelers (local)
- Farcaster (public 2023+)
    - hubs replicate all messages: libp2p gossip + diff sync,
      delta-state CRDT sets -> strong eventual consistency
    - spec: gossip alone does not guarantee SEC, hence diff sync
    - explicitly "weaker consistency guarantees", no consensus
      layer; identity registry on-chain (Optimism)
- Matrix (active)
    - room DAG replicated among member servers; backfill on demand
    - deterministic state resolution (v2) -> consensus on room
      STATE, but message order is per-server; permissioned per
      room (only member servers)
    - borderline Level 1/2; note in paper
- Hypercore / Holepunch (Keet, Pear; 2022+)
    - per-author logs; Autobase (2024) linearizes multi-writer
      logs deterministically among PERMISSIONED writers
    - borderline Level 1/2
- Automerge / local-first CRDT apps
    - convergence without order agreement

## Level 2: delivery and consensus

- Bitcoin, Ethereum (permissionless PoW/PoS)
    - total order of blocks; mempool txs best-effort, blocks
      reliably gossiped
- Hive (Steem fork 2020), DeSo (2021), Lens Protocol (2022+)
    - social/forum content on a blockchain (DPoS / L1 / L2)
    - consensus delegated to validators (semi-permissioned)
- Freechains (this paper)
    - permissionless, reputation-based order
